## 1. Summary

The loop FP-04 shipped captures the day's doings, but the day still has no closing ritual and no next-day spine: PRD §4.4's evening routine — journal → insights into core memory → targeted follow-up → a deadline-bound plan for tomorrow — does not exist, `anchor_plans` is an empty table the FP-04 eval reads through a forward-compatible empty input, and D14's Layer-2 JIT assignment has no anchors to assign inside of. The journal editor itself already ships (BG-10: distraction-free editor, block flagging, the Unsavable strip, local draft — zero network calls by design).

FP-05 builds the D16 evening chain end to end. One new sync function, `submit-journal` (GLOSSARY §13, §7.4): the client strips flagged blocks (D3 — the server never receives them), POSTs the permitted text, and gets an immediate ack — the sync path spends **zero provider calls** (pure inserts: one `journal_entries` row, one `journal_extract` job). The async chain then rides the existing jobs machinery: `journal_extract` runs one §4.3 extraction call (insights, vagueness, severity, plus the D20 rider fields), persists insights to `memory_facts` with one batched embed and full provenance, and stores vagueness/severity on the entry; a vague (≥ threshold) or non-S3 entry enqueues `journal_probe` — a targeted follow-up question in the chat thread (empathetic persona for S1/S2, the aggressive-editor reading for a vague S3) with a default-priority push; every extraction also enqueues `anchor_plan`, which generates tomorrow's plan (commitments, deadlines, routines, free blocks, boredom relief — PRD §3.1), validates it deterministically, upserts `anchor_plans` for the next day, and summarizes it in chat. Layer 2 lands in the pipeline: when a turn arrives inside a scheduled free block, stage 5 receives `{current_free_block, latest_energy}` and assigns a task in `direct_quote` (energy 1–3 → low-cognitive or boredom relief; 8–10 → heavy); with a plan present, any rescheduling attempt must win conversational approval — there is no calendar mutation API, the plan is authoritative.

Cost posture: **zero provider calls on the submit path**, at most three generation calls + one embed per user-day (extraction, conditional probe, plan), zero new job types (three of the fifteen §2.3-registered types get their handlers), **zero schema changes** (`journal_entries`, `anchor_plans`, `memory_facts`, `messages` all exist with the needed columns), one migration of four config keys, one new Edge Function. iOS remote push stays out ($0, §13 item 7) — the probe's push AC bakes the in-thread fallback; Web Push stays deferred (§13 item 9).

## 3. User Stories

1. **As a user winding down**, I write one distraction-free brain dump, flag the blocks I don't want read, and hit send — the app acknowledges in seconds and Davos reads it tonight; I am never waiting on an AI call to close my day.
2. **As a user whose entry was vague or heavy**, Davos comes to the chat with one targeted follow-up question — gentle when the day was genuinely rough, sharp when I am just dodging — so reflection does not end at "did stuff, felt meh".
3. **As a user**, I wake to a concrete plan for the day: fixed commitments, deadlines, routines, free blocks, and scheduled boredom relief, summarized in chat — the day has a spine before it starts, and moving any piece of it means talking it through with Davos first.
4. **As a user in a free block**, I just message Davos or answer a check-in — he assigns the right task for the block and my current energy: drained gets something light, charged gets the heavy lift.
5. **As the beta operator** (solo, $0), the evening adds at most three LLM calls and one embed per user-day behind free machinery (jobs table + dispatcher), the strip guarantees the server never holds flagged text, and a dead job leaves the entry un-extracted and visible — never silently mangled.

## 5. Non-Functional Requirements

| ID | Requirement |
|---|---|
| NFR-1 | **Latency**: submit ack p95 ≤ ~1 s server-side (pure inserts, no embed, no LLM — the entry itself is never embedded, §3.4 has no column for it); the chain completes within dispatcher latency (≤ ~2 min at the 1-min tick) |
| NFR-2 | **Cost ($0)**: per user-day worst case = 3 generation calls + 1 embed (extraction + probe + plan / insights); at 5 users ≈ 15 generate + 5 embed/day — inside §12's ~80/~250 projections with the existing 6×/4× headroom; zero new paid services |
| NFR-3 | **Determinism**: submit validation, date canonicalization, probe gate, all three idempotency guards, anchor validation, and the free-block resolver are deterministic; the LLM is confined to the three evening calls and the stage-5 rider on existing turns |
| NFR-4 | **Testability**: unit suites for the contract modules, resolver, guards, and submit state machine; `verify-fp05-stepN.py` gates for the server halves; a drill for the evening UX scripts cannot reach |
| NFR-5 | **Security**: journal content is untrusted input — capped, delimited, and wrapped with ignore-embedded-instructions copy in all three prompts (§10.5); service-role writes only; RLS unchanged; `tactical_analysis` stripped before anything is persisted |
| NFR-6 | **Privacy**: flagged text never leaves the device (the strip is upstream by design); journal facts carry `source_journal_id` provenance so a future purge path (item 7) can honor it; severity never reaches the client beyond the probe's behavior |
| NFR-7 | **Resilience**: a dead extraction job leaves the entry un-extracted (vagueness null) — visible in the jobs table, never silently mangled; a failed probe or plan never blocks the other (independent jobs); the plan upsert makes re-journaling safe; every handler is idempotent under double-fire (§2.2 clause 4) |

## 8. Risks

| ID | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| R-1 | Probe quality: the follow-up misjudges tone or target (a heavy entry probed sharply, or vice versa) | Medium | Medium | Severity-gated personas from config (flippable without redeploy); few-shot prompt keyed to the §11 criteria; the `[journal-extract]`/`[journal-probe]` lines are the tuning feed; S1/S2 can only ever route empathetic — the failure direction is the safe one |
| R-2 | Cold-start thin plans: `routine` is `{}` and habits/metrics are empty until their FPs land, so early plans rest on journal content alone | High (by design) | Low | The input set is forward-compatible by construction (empty = valid); the plan degrades to commitments/free blocks the journal implies; richness arrives with items 9–10 |
| R-3 | Late-night push: a user journaling past midnight gets the probe push at night (D16's accepted trade-off) | Medium | Low | Default priority (not high — §8); the summary is push-less; a send-hour window is a config-only add if observed in beta (recorded, deliberately not in v1) |
| R-4 | Duplicate submit: no server dedupe exists (spec-silent, no natural key) — a deliberate re-submit re-runs the chain | Low | Low | Single-flight client + draft cleared only on ack; the plan upsert keeps one row per date; a re-run probe is bounded by the `probed` guard per entry; recorded as a known trade-off |
| R-5 | Anchor validation rejects a semantically fine plan (overlaps the model legitimately wants) | Medium | Low | One corrected re-output carries the validator's errors into the retry prompt (the §7.9 pattern); second failure fails soft — no plan, a warning, tomorrow's journal regenerates; bounds are structural, not tuned |
| R-6 | Stage-5 rider regresses chat turns | Low | Medium | Riders are gated on plan existence — no-plan turns build a byte-identical prompt (AC-5); `verify-step11.py` + `verify-fp03-step7.py --static-only` + the FP-04 static gates re-run as regression legs |
| R-7 | Stub-shape drift repeats FP-04 Step 3a's lesson (a caller's validator rejecting the canned payload) | Low | Low | Both new shapes registered by validator identity in the same commit as their contracts; AC-8 runs the whole chain under stub mode |
