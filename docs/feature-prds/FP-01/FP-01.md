**Module 1 — Application Skeleton & Operational Foundation** (TECH-SPECS §14, steps 1–2, plus the Expo client shell).

Why this one and not a user-facing feature: (1) every later feature blocks on Auth, the `jobs` table, and the dispatcher — building any feature first means rework; (2) the keep-alive pinger is the difference between a project that survives its first idle week and one that silently dies (D12); (3) it closes the three §13 setup-day blocking checks, converting assumptions into verified facts before the LLM pipeline is built on them; (4) the client shell makes the skeleton tangible — a runnable app on all three platforms that every subsequent feature PRD plugs into. First LLM call, first rule, first check-in all come in FP-02+.

Feature PRDs are a new doc class: **execution plans subordinate to the four source docs** (AGENTS.md §2) — they decompose TECH-SPECS, never override it.

## 1. Summary

Stand up the runnable skeleton: an Expo Router app (iOS/Android/Web) with sign-in and an empty chat screen, backed by a Supabase project containing the core schema (migrations 1–6), a working jobs system (table + dispatcher + pg_cron tick), the mandatory keep-alive loop, and a Realtime subscription. No LLM calls, no AI behavior, no product features. Deliverable ends with the three §13 blocking assumptions closed and recorded.

## 2. In scope / Out of scope

**IN:**
- Expo Router TypeScript client, route map per §9, React Native primitives only
- Supabase project + migrations 1–6 (§3.5 order; migration 7 excluded — content-gated)
- Supabase Auth: magic link + Google OAuth (D25), client auth screens, `profiles` auto-creation
- `health` Edge Function + cron-job.org keep-alive (every 6 h)
- `jobs` table + `job-dispatcher` + pg_cron tick (§2.1–2.2, exact algorithm) + `smoke_test` job type
- Realtime subscription on `messages` (user-scoped) in the chat screen
- `config` table seeded with all §11 approved values
- §13 blocking checks 1–3 executed and written back into TECH-SPECS

**OUT (explicitly — do not build):**
- Any LLM/embedding call, provider adapter, pipeline stage, classifier, guardrails prompt
- Rules/exemplar content, onboarding interview logic, check-in loop, journal, dashboard rendering, Strike/trust/lockdown machinery
- Expo push notifications and `push_tokens` client code (table exists via migration; unused)
- Home-screen widgets (deferred post-beta, D1)
- The `select-persona`, `flag-unsavable`, `submit-*` Edge Functions
- Any AI response in the chat screen — it renders an empty thread with a disabled input placeholder

## 3. User stories

1. As a beta user, I can open the app on iOS (Expo Go), Android, and Web and reach the chat screen shell.
2. As a beta user, I can sign in with Google or a magic link on all three platforms and see my (empty) chat thread.
3. As the owner, I can insert a job row and watch the dispatcher claim, execute, and complete it; I can force failures and watch backoff and dead-lettering work.
4. As the owner, I can leave the project idle indefinitely without it auto-pausing.
5. As a developer, I can verify RLS blocks cross-user reads with a two-account test.

## 5. Non-functional requirements

- $0: Expo Go for iOS testing (no Apple Developer account), sideloaded Android build, web deploy on any free static host. No paid service touched.
- All Edge Functions Deno-compatible; dependencies verified before adding.
- Naming per GLOSSARY §10 (kebab-case functions, `snake_case` tables/config, `verb_noun` job types).
- No secrets in the client bundle or migrations — Supabase Edge Function secrets only.
- Dispatcher handlers idempotent by construction (uuid + status checks).

## 6. Acceptance criteria (all must pass)

- [ ] **AC-1:** `npx expo start` serves web; Expo Go opens the app on iOS; Android build installs. All five routes reachable; chat is the landing route.
- [ ] **AC-2:** Google sign-in and magic-link sign-in succeed on all three platforms; each creates `auth.users` + exactly one `profiles` row with FR-4 defaults.
- [ ] **AC-3:** Magic-link email arrives within 5 minutes (SMTP check result recorded per FR-10c).
- [ ] **AC-4:** Two-account RLS test: account A sees zero rows of account B in `messages`, `doings_logs`, `profiles`; anonymous API access returns zero rows.
- [ ] **AC-5:** `health` returns 200 from public URL; cron-job.org dashboard shows successful pings over 24 h.
- [ ] **AC-6:** Insert `smoke_test` job → within 2 min status transitions `pending → running → done`. Insert with `{"fail":true}` → observe `attempts` incrementing with backoff intervals → status `dead` at 5.
- [ ] **AC-7:** Service-role insert of a test row into `messages` for the signed-in user renders in the open chat screen within 2 s via Realtime; a row for a different user does not render.
- [ ] **AC-8:** `select * from config` returns every §11 key with the approved values.
- [ ] **AC-9:** TECH-SPECS §13 items 1–3 updated to "verified" with dated results; `smoke_test` registered in §2.3 + GLOSSARY §12.
- [ ] **AC-10:** Secret scan of the client bundle and migrations: clean.
- [ ] **AC-11:** Kill the dispatcher mid-job (deploy a sleep variant) → after 5 min the job resets to `pending` and re-executes (lease recovery, §2.2.3).

## 8. Risks

| Risk | Mitigation |
|---|---|
| Google OAuth redirect URIs across Expo Go / Android / Web is the known time sink | Budget one full session for it; configure the Expo scheme first, then add platform URIs |
| `pg_net` HTTP call from pg_cron blocked or delayed on free tier | AC-6 catches it; fallback per §2.2 note — the tick only *enables* claiming, a missed tick costs ≤1 min latency |
| Built-in SMTP rate/deliverability limits break magic links | FR-10c exists to surface this now; if broken, Google OAuth remains primary and SMTP becomes a live item |
| Idle auto-pause despite pinger | cron-job.org logs verify pings; 7-day survival is observational post-launch — leave a calendar reminder on day 8 |
