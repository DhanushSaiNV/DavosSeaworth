## 1. Summary

The front door has never been built. Every onboarding surface has stood empty since the earliest migrations: `profiles.onboarding_stage` defaults to `'intro'` for all five beta accounts, `wake_time`/`sleep_time` are null, `routine` is `'{}'`, `high_dopamine_activities` is `'[]'`, `metrics.is_core` is false everywhere, and `fact_type='baseline'` has no writer — FP-06's retrieval has been including an always-empty baseline block on every turn since it shipped. §7.1's own as-built note parks the watchdog's onboarding-stage gate on this FP; FP-08 recorded three seams here (the empty-activities preemptive degradation, the §7.5 habit-topic suppression key, and the last unimplemented job type); and D17's resume state machine, D22's alternatives question, and §7.7's chip-based metric selection have no code at all. Meanwhile, the background content deliverables have established the library: 144 owner-approved rules across all 16 canonical domains are live in `rules` with embeddings (placeholder rules cleared), 228 approved canonical exemplars are live with `source='BG-04'` (placeholder exemplars cleared; 233-row revision prepared in `exemplars.csv`), `content-seed` is deployed with bearer authentication, and `_shared/content.ts` is ratified on the canonical 16 domains.

FP-09 builds the interview as wiring over the standing pipeline. A signup trigger fn writes the deterministic opening message (config text — a trigger cannot await providers, the `sync_degrade_reply` precedent), and the state machine on `profiles.onboarding_stage` advances on a deterministic question clock: each onboarding user row is stamped with its stage, and the stage flips — compare-and-set, crash-safe — when the stage's configured question count is answered. The per-turn §4.3 extraction gains an optional onboarding block (profile field updates + baseline facts) so data capture rides the call stage 1 already makes — zero extra provider calls — with each fact reusing the turn's embed (baseline facts are always-included in retrieval, so vector fidelity is not load-bearing) and per-field fail-open validation. Stages 4–5 gain an interview override at exactly the point FP-08's lockdown override already reads profile state: persona locked to `onboarding_persona`, no rules block in the prompt (the interview asks; it does not preach — and interview prompts stay independent of the live rules library), generation instructed to ask question N+1 or acknowledge-and-transition at the boundary. `metric_selection` proposes 3 presets as `ui_metadata.metric_options` chips — selected deterministically from the interview turns' classified domains (the classifier's first onboarding consumer), catalog-order fallback — and a new `select-metrics` function, the FP's only new function, turns 1–2 taps into `metrics (is_core=true, formula=preset)` rows through `insertValidatedMetric`; the dashboard renders them with zero FP-07 changes. The `(onboarding)/interview` route reuses the whole thread machinery (Realtime, composer, optimistic bubbles, offline queue) minus the tab bar, plus a stage indicator; the root route gate keeps incomplete users out of `(app)`, which structurally disarms the check-in scheduler and deep-links bounce home. The `proactive` job closes the registry at 15/15: a guarded 30-min tick inserts per-user jobs in two local windows (10:00, 19:30 `[SPEC]`) for complete, silent users; the handler asks about the first missing profile field (deterministic gap order) or sends a light companionship message, as an unprompted row + default-priority push — and its prompts carry no habit/watch/impulse context at all, which is FP-08's recorded suppression seam resolving structurally. The content integration delivers BG-06 (onboarding opening copy and stage prompt scripts) and validates the RAG boundary: clean intake suppression, active rules retrieval post-intake, and validation clean across the live library.

Cost posture: **one job type implemented — the registry closes at 15 of 15**, **one new sync function** (`select-metrics`, zero providers), **zero schema growth** beyond `0032` (`profiles.onboarding_stage` and every field it writes have stood since `0002`/`0007`; migration `0033` is a trigger, a tick fn, and 8 config seeds), **zero new per-turn provider calls** (the block rides stage 1; facts reuse the turn embed), onboarding ≈ 11 generated turns one-time per user, `proactive` ≤ 2 generates per user-day, scheduled inserts ≈ 451/day vs the ~500 §2.3 line (the recount lands in §12), zero bulk re-embedding needed (the 348 embeds were already completed in BG-03/BG-04), and the proactive push carries the standing §13-item-7 iOS fallback (in-thread on next open — the FP-04/FP-05/FP-08 amendments' pattern). One live-behavior change is flagged to the owner up front: the day this merges, every existing account sits at `'intro'` and enters the interview at next open (the backfill plants their opening row).

## 3. User Stories

1. **As a new user**, the app opens straight into Davos — no forms, no wizard — and he speaks first: one opening question, then a short interview that actually listens; if I close the app mid-conversation, nothing is lost — he picks up exactly where we stopped when I return (PRD §4.1, D17).
2. **As a user finishing intake**, Davos hands me 3 metric chips rooted in what I just told him — I tap the one or two that matter, and my dashboard is alive the same day with numbers I chose, evaluated nightly from my own logged doings (PRD §3.5, §4.5; D10/D17).
3. **As a user who has gone quiet**, Davos does not wait: a light message when I've been silent, and when my profile has a hole — no wake time, no alternatives list, too few known facts — he asks about exactly that, conversationally, until the gap is filled (PRD §3.0, §3.4; the `proactive` job, §2.3's last type).
4. **As the owner-as-content-editor**, the 144-rule library across all 16 canonical domains and the 228/233 exemplars are live, and the onboarding flow speaks in Davos's authentic voice from the first line without lecturing me before learning my story (PRD §4.1; D17; AGENTS §8.4).
5. **As the beta operator** (solo, $0), the last job type closes the registry at 15/15 with zero schema growth and one new zero-provider function; every trigger is deterministic with the LLM confined to asking and composing behind those gates; two kill switches and a config-bounded cadence bound the proactive loop; and the content library is clean and verified.
