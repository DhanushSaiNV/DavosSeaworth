## 1. Summary

While `app/(app)/dashboard.tsx` has layout and profile check-in cards, the dynamic metric visualization layer, formula validation gate, and nightly metric evaluation remain unimplemented: `metrics` and `metric_points` have stood since `0007` with no writer, no evaluator, and no reader beyond `anchor_plan`'s context pull. PRD §3.5's Proof-Based Life Dashboard — "numbers motivate more than hormones" — has none of its three pillars: no visualization layer (decisions2 D9 / TECH-SPEC D10 pre-built component registry), no formula path (the JSONLogic validation gate is §10.4's "only evaluable code path in the system" and does not exist), no nightly evaluation (the `metric_eval` job is registered in §2.3 but unimplemented). PRD §4.5's fifth beat — "the user occasionally steps out of the chat into the Life Dashboard to view visual, metric-based proof of their progress" — has nowhere to land.

FP-07 builds all three pillars. **Data plane:** a `metric_vars_daily` SQL view computing seven of the eight §7.9 variables per user per local day, plus the eighth (`checkin_compliance_rate`) computed through the existing frozen server grid — deliberately not a SQL twin — and a guarded pg_cron insert that fires one `metric_eval` job per user at 00:30 local for the day just ended; the handler evaluates every active metric's gate-passing formula and upserts `metric_points`. **Gate:** a pure deterministic validator (whitelisted ops, whitelisted variables, literal/depth/node bounds, arity/type checks) and a hand-written recursive evaluator — the model's raw output is parsed and gated, never string-evaluated, and a formula that fails the gate can never be persisted through any path. **Surface:** the real dashboard screen — four pure registry components (`TrendLineGraph`, `ConsistencyHeatmap`, `ProgressBar`, `StatCard`) consuming `{metric_id, points[]}` and nothing else, read through PostgREST under the RLS that already stands. To make the loop real on day one, FP-07 also ships an in-code core-metric preset library (the §7.7 `formula=preset` source for item 10's chips) planted through a dev-smoke seed action, and the full AI-proposal chain §7.9.4 describes — one corrected re-output on gate failure, then the described-metric fallback — as a shared module with no caller until items 9/10 wire their acceptance flows to it.

Cost posture: **zero provider calls anywhere in the daily loop** (evaluation is SQL + TypeScript; the cron ticks are guarded inserts inside the standing scheduled-insert budget), zero per-turn changes to any pipeline path, one generation call per proposal attempt (drill-only until items 9/10), **zero new job types** (the tenth of fifteen registered types gets its handler), **zero new tables or columns** (migration `0031` is one view, one guarded cron function + schedule, three config seeds), zero push surface, **zero new client dependencies** (`package.json` untouched; `react-native-svg` is already installed in the repo and available), and — a first since FP-01 — **zero edits to any FP-02..06 file**: the only pre-existing files touched are the dispatcher registry and `dev-smoke`, the standing per-FP growth points.

## 3. User Stories

1. **As a user doing the daily work**, I open the dashboard and see numbers that moved because I showed up — hours logged, check-ins kept, energy held — visual proof the effort landed (PRD §4.5), not a motivational platitude.
2. **As a user who starts with core metrics**, my dashboard begins with the ones chosen for me and grows as Davos proposes more — and every number on it is computed the same deterministic way every night: what the formula says is what the chart shows, nothing hallucinated.
3. **As a user on any platform**, the dashboard is the same screen with the same components — no OS permissions, no notifications, no install step — because every visualization comes from one closed pre-built registry.
4. **As a user whose mentor invents a metric for a neglected domain**, the formula behind it survived a deterministic gate before it ever touched my data — and if it couldn't, Davos describes the metric in plain words instead of silently shipping broken math.
5. **As the beta operator** (solo, $0), nightly evaluation costs zero provider calls, a bad or injected formula can neither execute nor persist (the whitelist is the whole attack surface), a dead job is one drill command from recovery, and one config flip (`metric_eval_enabled`) stops the loop cold with no redeploy.

## 8. Risks

| ID | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| R-1 | Zero-data days mislead (energy_avg 0 reads as "exhausted" on a day with no energized logs) | Medium | Medium | The zero-data list is logged per run; presets avoid raw `energy_avg` alone (guard with `doings_count`); the tuning surfaces are the preset library and the proposal prompt, and the drill makes the semantics owner-visible |
