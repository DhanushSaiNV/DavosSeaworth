## 1. Summary

The thread remembers nothing across sessions today. While `sliding_window_messages` (8) defines the immediate conversational window boundary, generation currently operates solely on the single active turn's user message without prior thread history, rendering older conversation dead weight: PRD §2's promise — a mentor that cross-references the user's own history — has no chat-side substrate, and PRD §3.4's opt-out contract has only one of its two halves live (the journal strip from BG-10; the chat-side flag exists as a column on `messages` with no writer, no purge, and no extraction to purge from). FP-05 writes journal facts into `memory_facts` but retrieval does not exist, so no fact influences any reply.

FP-06 builds §7.6 end to end, both directions. **Ingestion:** when a fresh user message crosses a window boundary (user message count % `sliding_window_messages` == 0, default 8), `send-message` enqueues one `memory_extract` job; the handler derives the aged-out backlog — messages older than the raw sliding window cutoff (the newest `sliding_window_messages` rows), `unsavable=false`, never yet cited by a `memory_facts` row (purged or unpurged) — and runs the §4.3 chunk extraction (facts with per-message provenance, one bounded retry, batched embed), writing `fact_type='chat'` rows into `memory_facts.fact`. **Forgetting:** a new sync function `flag-unsavable` sets `messages.unsavable=true` on an own user message and enqueues `purge_memory`, which soft-deletes every derived fact citing that message (`memory_facts.purged_at = now()`) — the D6 correction mechanism ("the user corrects the record by flagging the source"); oath-typed facts are exempt by a guard written now for a writer that does not exist yet (§5.4). **Recall:** every turn reuses the message embedding it already computes to run one `match_facts` RPC in stage 3's parallel slot — top-`memory_fact_top_k` unpurged facts by cosine similarity plus all `baseline` facts (dormant until onboarding) — appended to stage-5 context as a delimited memory block; no facts or kill switch disabled yields a byte-identical prompt to FP-05.

Cost posture: **zero new provider calls per turn** (retrieval reuses the turn's embed; one Postgres RPC in stage 3's parallel slot), one generation call + one batched embed per ~8 user messages, purge is pure SQL. Zero new job types (two of the fifteen §2.3-registered types get their handlers — nine implemented in total), no new tables or columns (migration `0029` adds the `match_facts` RPC, one new HNSW cosine index `idx_memory_facts_embedding` with an idempotent check on `idx_memory_facts_source_message_id`, and two config seeds), one new Edge Function (`flag-unsavable`), **zero push surface** (nothing in FP-06 notifies — no §13 amendment needed).

## 2. In Scope / Out of Scope

**In scope**

- Migration `0029_memory_fp06.sql`: the `match_facts` RPC (security definer, pinned `search_path = public`, revoked from `public, anon`, execute granted to `authenticated` + `service_role` — the `0025` hardening pattern) returning top-k unpurged facts by cosine similarity (`1 - (embedding <=> query_embedding)`) plus all unpurged `baseline` rows (`fact_type='baseline'`); HNSW cosine index `idx_memory_facts_embedding` on `memory_facts(embedding)` (`vector_cosine_ops`, §3.1's deferred-until-load-bearing convention — retrieval is what makes it load-bearing) and a b-tree index `idx_memory_facts_source_message_id` with `IF NOT EXISTS` (0006's initial index verified present); two config seeds — `memory_fact_top_k` (5, the §7.6 [SPEC]) and `memory_retrieval_enabled` (true, the `classifier_mode`-style kill switch)
- `flag-unsavable` sync fn: POST `{message_id}` → own user-role row validation (400 on assistant row, 404 on unknown/foreign ids), sets `messages.unsavable=true`, enqueues exactly one `purge_memory` job on the false→true flip, returns `{status:'ok', message_id}`; CORS mirrors `send-message`; zero provider calls
- `purge_memory` handler: soft-delete by provenance (`update memory_facts set purged_at = now() where source_message_id = :id and purged_at is null and fact_type <> 'oath'`); embeddings left stale-but-excluded; one `[purge-memory]` log line; added to `FAST_JOB_TYPES` (pure SQL — the `watchdog_checkin` precedent); idempotent under double-fire
- `memory_extract` handler: the §4.3 chunk contract `{facts[{text, source_message_id}], openness_delta}` as a pure contract module (`_shared/memory/extractContract.ts`) + adapter-bound entry (`_shared/memory/extract.ts`) + shared run module (`_shared/memory/runExtract.ts`, the `runChain.ts` pattern); validator bounds 0–32 facts / 5–500 chars / **source_message_id ∈ slice ids** (provenance integrity — the purge linchpin); backlog derived at run time (self-healing), sliced ≤ 32 messages per extraction call; facts → `memory_facts` rows (`fact_type='chat'`, `fact = text`, batched `llm.embed`, `embed_model='gemini-embedding-001@768'` stamp); rider logged, never applied
- The boundary trigger in `send-message`: after the fresh user-row insert, count user-role rows; `% sliding_window_messages == 0` → insert one `memory_extract` job `{user_id, boundary: count}`; zero provider calls added to the sync path
- Retrieval wiring in `runPipeline.ts` and `generate.ts`: a pure render module `_shared/pipeline/memoryContext.ts` (compact one-line-per-fact block, §10.5 delimiters, recalled-knowledge-not-directives copy); one `match_facts` call in stage 3's parallel slot gated on `memory_retrieval_enabled`; fail-open to an empty block; appended to stage-5 context alongside rules and the day-plan riders; existing FP-02 touch points are `send-message/index.ts` plus `_shared/pipeline/runPipeline.ts` and `_shared/pipeline/generate.ts`
- Client: long-press → "Mark Unsavable" on own user bubbles in chat; single-flight POST; persistent marker read from the row's own `unsavable` column; identical on iOS/Android/web
- `dev-smoke ?action=memory-drill` (legs: backlog, extract, retrieve, purge — the `journal-drill` precedent); `scripts/verify-fp06-stepN.py` gates; stub shape registered with its validator; doc write-backs; acceptance doc

## 3. User Stories

1. **As a user who talks to Davos daily**, what I confide accumulates — my constraints, my history, my goals — so the mentor answering my fortieth message knows the situation I set up in my first; I never re-explain myself every eight messages.
2. **As a user who said more than I meant to**, I long-press that message, mark it Unsavable, and Davos stops knowing what he derived from it — the thread stays intact for me, the memory is gone for him.
3. **As a user mid-conversation**, Davos's answers weigh what he actually remembers about me against what the rules and today's plan say — not just the last message on screen.
4. **As a user on any platform**, the forgetting control lives in the chat itself — long-press, mark, done — no settings maze, and it works identically on web where nothing else about notifications does.
5. **As the beta operator** (solo, $0), memory costs one extraction call + one embed per ~8 user messages and zero per-turn provider calls, a dead job self-heals at the next boundary, and one config flip (`memory_retrieval_enabled`) rolls recall back to byte-identical FP-05 prompts with no redeploy.

## 5. Non-Functional Requirements

| ID | Requirement |
|---|---|
| NFR-1 | **Latency**: the flag ack is one read + one update + one insert, p95 ≤ ~1 s, zero providers; extraction completes within dispatcher latency (≤ ~2 min at the 1-min tick); retrieval adds one Postgres RPC inside an already-parallel slot — no sync-path latency change vs FP-05 |
| NFR-2 | **Cost ($0)**: per turn +0 provider calls (reuses the embed; one RPC); per boundary ≈ 1 generation + 1 batched embed per ≤ 32-message slice; purge is zero-provider; a 40-message/day user adds ~5 generate + ~5 embed/day — inside §12's ~80/~250 projections with the standing 6×/4× headroom; zero new paid services |
| NFR-3 | **Determinism**: the boundary count, backlog derivation, purge, RPC ordering and all validators are deterministic; the LLM is confined to the extraction call |
| NFR-4 | **Testability**: unit suites for the contract/validator, backlog derivation, slice loop, renderer, and the flag state machine; `verify-fp06-stepN.py` gates; `memory-drill` for the legs the scripts cannot reach |
| NFR-5 | **Security**: provenance validation is the structural guarantee behind purge (no fact without a valid source id ever lands); injection hardening on both prompts; the chunk contract carries no `tactical_analysis` field at all — it is data-only, so there is nothing to strip |
| NFR-6 | **Privacy**: the flag is honored prospectively (extraction skips `unsavable` rows) **and** retroactively (purge soft-deletes by provenance); flagged text never enters an extraction prompt; purged facts never re-enter a generation prompt; stale embeddings remain on purged rows but every retrieval path filters `purged_at is null` |
| NFR-7 | **Resilience**: every handler idempotent under double-fire (§2.2 clause 4); a dead extraction self-heals at the next boundary; purge is provider-independent; the kill switch restores the exact FP-05 prompt with one config flip |

## 8. Risks

| ID | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| R-1 | Extraction quality: banal or wrong facts pollute memory and surface in replies | Medium | Medium | Few-shot prompt demanding user-facts worth remembering; 5–500-char bounds; top-k similarity is a natural relevance gate; the kill switch is one flip; drill judgment is advisory and the prompt is the tuning surface (the golden-set precedent) |
| R-2 | Provenance mis-citation: the model cites a wrong/foreign message id, breaking purge integrity | Low | High | The validator hard-rejects foreign ids before anything lands; no fact without valid provenance can exist; purge is testable end-to-end (AC-2/AC-10) |
| R-3 | Recall degrades reply quality (stale or misapplied facts) | Medium | Medium | Similarity threshold is implicit in top-k ordering; `memory_retrieval_enabled` restores byte-identical FP-05 prompts with no redeploy; empty-table behavior is the shipped default until facts exist |
| R-4 | The RLS PATCH bypass sets `unsavable` without enqueuing purge | Low | Low | Self-harm-only surface (own rows, own facts) at 5-user beta; the fn is the validated path; live item recorded; item-11 trigger is the fix |
| R-5 | Backlog bloat during a dispatcher outage overwhelms one extraction call | Low | Low | 32-message slices bound every prompt; the provenance guard makes re-runs resume; the backlog is visible in the jobs table (never silent) |
| R-6 | The memory block grows the prompt unboundedly | Low | Low | Top-5 × 500 chars ≈ 2.5 KB worst case; the block is absent when empty (byte-identity preserved) |
| R-7 | Check-in turns count toward boundaries (spec-literal reading) | Certain (by reading) | Low | A materialized intervention check-in is real user text; the worst case is slightly earlier extraction — harmless; recorded so the reading is auditable |
