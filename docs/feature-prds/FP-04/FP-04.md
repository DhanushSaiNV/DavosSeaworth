## 1. Summary

The pipeline FP-02 shipped answers chat messages; the classifier FP-03 made those answers real. But PRD §3.1's accountability heartbeat — the hourly/bi-hourly "What did you do this hour?" loop that feeds the doings memory engine — does not exist yet, and §6.1's energy input is dormant with no check-in turn to carry it (TECH-SPEC §6.1 as-built note: "the §6.2 override is dormant until the check-in FP threads `profiles.latest_energy` through it").

FP-04 builds the D9 loop end to end. The client pre-schedules a **rolling 24 h window of local notifications** (deterministic ids, cadence and active hours from `profiles`, one missed reply never affects the next) with a Reply text-input action and a deep link into chat. Three capture paths converge on one new sync function, `submit-checkin` (GLOSSARY §13; TECH-SPEC §7.1): OS direct reply, deep-link/banner chat mode, and the web in-app banner. The function is **deterministic-first** (D9): parse the trailing 1–10 energy digit server-side, insert the `doings_logs` row with one embed (the same `llm.embed` every vectorized row uses), update `profiles.latest_energy` — and spend **zero LLM calls** unless a deterministic gate trips (energy ≤ 3, or the window answered more than 15 min late). A gated turn runs one small evaluation call (`{deviation, intervention}`) against today's anchors; only `intervention: true` materializes the turn in chat and runs the §5 pipeline — **with the energy threaded**, activating FP-03's override. A closed window the watchdog finds unanswered (pg_cron → `watchdog_checkin` job → `intervention` job) produces an unprompted in-chat nudge plus a high-priority push.

Cost posture: **one embed per check-in, LLM only when gated, zero new job types** (two of the fifteen §2.3-registered types get their handlers), two migrations, two new config keys, one index, one small RPC. iOS remote push stays out ($0, §13 item 7) — its ACs bake the fallback (local notifications + in-chat intervention on next open); Web Push stays deferred (§13 item 9) — web runs the in-app banner.

## 3. User Stories

1. **As a user in flow**, I get one short prompt at the end of every hour and can answer it from the notification itself — "finished the report, drained 4" — so accountability costs me ten seconds and never an app open.
2. **As a user**, my energy arrives with my words (trailing digit or a quick-tap chip), so Davos reads my state the way a coach would: drained gets empathy, fired-up gets push — the persona follows the number, not a guess.
3. **As a user who goes silent**, the missed window does not slip by: Davos notices within minutes and comes to me in chat (with a push where the platform allows), so ignoring the loop is not a strategy the app tolerates.
4. **As a user drifting off-plan**, a low-energy or late check-in is evaluated against my day right away, so the confrontation happens within the hour it happened, not at midnight when the day is already lost.
5. **As the beta operator** (solo, $0), the loop rides free machinery only — local notifications, one embed per check-in, LLM calls strictly behind deterministic gates — and web/iOS degrade to specced fallbacks instead of paid services.

## 5. Non-Functional Requirements

| ID | Requirement |
|---|---|
| NFR-1 | **Latency**: on-track submit p95 ≤ ~3 s server-side (one embed + inserts, no LLM); an intervention turn is bounded by the existing `pipeline_deadline_ms` guard and degrades rather than being killed — no new deadline arithmetic |
| NFR-2 | **Cost ($0)**: per on-track check-in = 1 embed; the eval call only on gated turns; full pipeline only on intervention. At 5 users × ~14 windows/day ≈ 70 embeds/day — inside §12's ~250/day embedding projection — plus bounded gated calls; no new paid service (local notifications are free; no Apple Developer Program) |
| NFR-3 | **Determinism**: window grid, ids, energy parse, gates, watchdog dedup — all deterministic; the LLM is confined to the gated eval call and the intervention generation |
| NFR-4 | **Testability**: unit suites for parse/grid/gates/dedup/§5.3-exclusion; `verify-fp04-stepN.py` gates for the live server halves; a device-drill checklist for the notification UX scripts cannot reach |
| NFR-5 | **Security**: `windowTs` is untrusted input — recency-bounded **and canonicalized server-side** to the grid window before it is stored or deduped (FR-5), so a shifted or off-grid hint can neither forge a second doing nor dodge the watchdog join; the prefs RPC is column-restricted (`trust_score`, `dialog_state` unwritable by construction); RLS unchanged; service-role writes only |
| NFR-6 | **Privacy**: direct-reply check-ins have no unsavable affordance (an OS reply cannot flag — accepted; D6 is a UI-surface concept); chat-path rows carry the flag like any message, which later memory extraction respects |
| NFR-7 | **Resilience**: a killed app never loses future check-ins (rolling pre-schedule); a failed POST never loses a reply (pending store); a missed dispatcher tick costs ≤ latency, never data (D2); the client/server grid twins share test vectors — drift between them is a stop condition |
