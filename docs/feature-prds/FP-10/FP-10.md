## 1. Summary

Nine FPs have left a machine that is guaranteed only in slices. Every handler shipped with its guards and every FP's gates asserted its own surfaces — the 15 job types × their dedups, the eight sync fns × their dedupes and 23505 winner-returns, the cron tick guards, the three client queues × their replay keys — but no pass has ever swept them as one register, and §2.2's dispatcher semantics (snooze, budget release, lease reset, the backoff schedule) have never been re-proven since FP-08 introduced the fourth of them. Meanwhile the hardening debts accumulated by deliberate design: FP-04 recorded the `profiles` own-row grant as a live item; FP-06 recorded the `messages` PATCH bypass (`unsavable` set directly, purge never enqueued) and named a DB trigger as the item-11 fix; FP-08 added the snooze convention, left `oath_request` rows that can sit unconsumed forever — with a capture rule that would enshrine whatever the user next says, days later and unrelated, as a purge-exempt oath — and FP-07 parked formula-edit re-evaluation here; §5.1 accepted a residual window where a killed invocation leaves a holding reply with no `llm_retry` job behind it; FP-09 added `onboarding_stage` to the hand-PATCH list and handed this FP the final `dev_overrides_enabled` flip. §14 ends with exactly this: item 11 — the hardening pass.

FP-10 adds no features. It is one DDL migration, three drill harnesses, one audit document, and one config flip. The migration makes the permission model match the spec's own letter: column-level grants on `profiles` (`display_name` alone stays client-writable) and `messages` (`unsavable` alone), INSERT/UPDATE/DELETE revokes on every table whose writers are all service-side, the `trust_events` read closed (§3.4 says server-only; the grant finally agrees — the hidden score's audit trail stops being client-reconstructable), and the `unsavable` false→true flip becomes a trigger-enqueued `purge_memory` job — the raw PATCH and the validated `flag-unsavable` fn become behaviorally equivalent, which is a stronger fix than blocking the bypass. The atomic holding+retry pair closes §5.1's residual structurally (both rows land or neither; the imagined reconciliation sweep becomes a one-time count, expected zero). The oath capture gains a freshness window so a stale demand cannot capture an unrelated message. The drills then prove the mandate's three nouns: the **idempotency audit** (a matrix of every write path × guard × replay verdict, plus a live double-fire harness), the **prompt-injection tests** (a corpus through every user-text entry point, a static gate over every prompt builder, live marker-absence assertions), and the **provider failover drill** (both tiers failed and restored, sync and async paths, the embed single-provider reality, timed against §12's budget).

The closing act is the beyond-beta gate: the config hygiene table (every dev-only key at its safe value), `dev_overrides_enabled` → `false` as the FP's final committed act once every drill is green, and the §13 item-4 quota re-verify run owner-side with numbers and dates recorded. Cost posture: **zero client diffs** (asserted by `git diff`), **zero new job types** (15/15 stands, final), **zero columns and zero tables**, one trigger fn, one config seed, the enumerated server touch set; one-time drill quota ≈ 60–90 provider calls total; the ~451/day scheduled-insert line stands unchanged. When this tracker closes, §14's list is done — the project's entire implementation order, eleven items, shipped and hardened.

## 3. User Stories

1. **As a user who flagged a message unsavable**, the forgetting actually happens no matter which door the request walks through — the validated button, or a hand-crafted API call against my own row: both land the flag, both enqueue the purge, neither silently skips it (PRD §3.4; D3/D6; the FP-06 live item dies).
2. **As a user**, the thread is what the system says it is: nobody — not even me, with my own credentials — can forge Davos's words into my thread, rewrite history, or read the hidden trust trail the design says I shouldn't see; my data is mine to read, the machine's to write (§3.1–3.4, §10; D20's "hidden by design").
3. **As the owner-as-operator**, everything happens exactly once: a double-send, a double-tap, a re-fired job, a double tick, a replayed queue entry — each is a no-op or a repair, and I hold one document that says so for every write path in the system, with evidence (§2.2; the idempotency audit).
4. **As the owner-as-operator**, a provider outage is a rehearsed non-event: one tier down is invisible, both tiers down degrades gracefully and recovers, the async jobs back off and come home — and I have the measured numbers to prove which budget actually bound (§4.1, §12; D18).
5. **As the owner about to invite user #6**, the gate closes behind me: dev overrides off, quotas re-verified against today's free-tier terms, grants least-privilege, and §14's list — all eleven items — done; what remains unfinished is written down as post-beta scope, not hiding in a live-items list (§13, §14).
